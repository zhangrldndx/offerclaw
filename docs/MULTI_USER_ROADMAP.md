# OfferClaw 分发与数据主权模型(如何"让更多人用")

> 定位:**OpenClaw 式本地优先开源软件**——用户从 GitHub 获取,部署在
> 自己机器上,用自己的 API key,数据(知识库/画像/日志/用量)全部落在
> 用户本地磁盘。**项目开发者看不到任何一台安装的任何数据**(本项目
> 不含遥测上报代码)。"用户增多" = 分发与安装体验,不是账号系统。

## 1. 三种部署形态与数据归属

| 形态 | 谁在用 | 数据在哪/谁可见 | 需要什么 |
|---|---|---|---|
| **本地单人(主模式)** | 用户本人,GitHub 下载自装 | 用户磁盘;仅用户可见 | 什么都不用加:一人一实例一画像,换岗位方向 = 改画像/方向配置(audience 路由已支持) |
| 共享实例(可选) | 实验室/小团队内网一台机器 | 那台机器;需要租户隔离 | `tenancy.py` 接缝为此预留(请求头切租户、collection 命名空间、用量归属维度),单人模式下零行为变化 |
| 托管 SaaS(远期,不承诺) | 公网注册用户 | 运营方服务器;需合规 | 鉴权/配额/per-tenant 评测——仅当真要做时再动,接缝已立 |

## 2. 数据主权声明(开源发布时写进 README)

- 知识库(chroma_db/)、画像、日报、投递记录、LLM 用量账本:全部本地文件,不上传;
- 出网流量只有两类:用户自己配置的 LLM API 调用、用户自己接的推送渠道(微信);
- `usage_report.py` / `GET /api/stats` 是**用户看自己**的运营看板,不是上报;
- 无遥测。若未来想统计安装量,只做**默认关闭的 opt-in** 匿名计数,并在 README 显著声明。

## 4. 容量边界(实测,答"一台机器能撑多少"用)

合成压测(异机):1万/5万/10万 chunks 纯向量查询 p50 35/39/39ms(查询不是
瓶颈);RSS 1.3/1.5/1.9GB(≈6-7KB/块),入库线性 14/67/136min。单机对
个人知识库规模绰绰有余;共享实例场景下先到的瓶颈是入库时长与内存。
